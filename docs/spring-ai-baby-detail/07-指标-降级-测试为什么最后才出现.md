## 一、先看 `AiMetricsService`

它不是业务逻辑类。

它是统一打点类。

为什么要单独抽出来？

因为如果每个类都自己乱写 metrics，后面会很散。

### 你现在项目里 metrics 大概在记录什么

- chat 次数
- chat 延迟
- stream 次数
- stream 延迟
- fallback 次数
- rag 命中文档数
- knowledge rebuild 次数

### 这些指标为什么有价值

因为你以后可以回答这些问题：

- 哪个场景最常被问？
- 哪个场景最慢？
- fallback 有没有突然变多？
- rag 一般命中几条？

## 二、为什么一定要做 fallback

AI 不是稳定函数。

它的失败来源很多：

- 上游模型挂了
- 结构化输出不合法
- 工具失败
- 配置出错

如果没有 fallback，你的接口一出问题就是 500。

但你现在做了 `DEGRADED`，它的意义是：

- 接口结构不崩
- 前端还能正常显示
- 会话还能连续
- metrics 还能统计失败

这很重要。

## 三、为什么测试在最后

因为测试不是先写才知道测什么。

你得先有这些东西：

- scene
- tool
- rag
- session
- stream
- metrics
- fallback

然后你才能知道：

`哪些是最容易被后续改坏的边界。`

## 四、现在这套测试在保什么

### 1. 场景计划

比如 system 场景有没有真的挂上 RAG 参数。

### 2. 主编排器

比如：

- degraded fallback
- toolStatus 映射
- scene reuse
- usage / retrieval
- stream 完成后的写回

### 3. 会话系统

比如：

- session detail 分页
- rename
- clear
- appendTurn 更新摘要和索引

### 4. controller 契约

比如：

- 参数有没有透传
- 校验有没有生效
- knowledge status / rebuild 是否返回正确

## 五、为什么这些测试不是“可有可无”

因为你现在这个 AI 模块已经不是一个文件了。

它已经跨了：

- controller
- service
- memory
- rag
- tool
- metrics

这种时候如果没有测试，你每改一处都只能手工点接口碰运气。
